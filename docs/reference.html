Циклы на пиксель#

Цена шейдера — сколько тактов ядро Mali тратит на один его запуск: на один пиксель (фрагментный шейдер), одну вершину (вершинный) или один поток (compute). Её считает Mali Offline Compiler (malioc) для каждого ядра, без устройства.

цена = такты самого загруженного блока ядра на самом длинном пути через шейдер

Ниже — что это за блоки, почему берётся самый загруженный и что такое самый длинный путь.

Это не миллисекунды. Цена показывает, сколько работы шейдер даёт ядру. Сравнивать её стоит между шейдерами на одном ядре.

Блоки ядра Mali#

В шейдерном ядре Mali несколько блоков (конвейеров), и работают они одновременно.

Как A складывается из частей. На G57–G78 A — самая загруженная из FMA, CVT и SFU (они работают параллельно). На G610/G710 части делят выдачу команд, и A ≈ FMA + CVT + SFU/4. На G715/G720 — между этими крайностями. У Bifrost (G52) блок арифметики один, частей malioc не показывает.

Упор (bound)#

Раз блоки работают одновременно, шейдер не выполнится быстрее своего самого загруженного блока, а работа остальных «прячется» за ним. Этот блок и называется упором. В отчётах он показан как «LS память», «SFU спецфункции» и т.п.; его такты и есть цена.

Главное правило: экономия в блоке, который не упор, цену почти не меняет. Если шейдер упирается в LS (память), сокращение математики его не ускорит — пока арифметика не станет больше LS.

Пример: LS 36, арифметика 21, T 4.3 → цена 36, упор LS. Убрать половину математики: цена так и останется 36.

Если упоров два (например FMA+CVT), они загружены одинаково.

Пути: длинный, короткий, всего#

  • Самый длинный путь — самый дорогой путь через шейдер: каждый if идёт по более дорогой ветке. Цена считается по нему, то есть это оценка сверху для одного запуска.
  • Самый короткий путь — все ветки идут по дешёвой стороне. Вместе с длинным даёт разброс.
  • Всего — каждая инструкция посчитана один раз: обе ветки if, тело цикла один раз. Это объём кода, а не время: может быть и больше, и меньше длинного пути.

Если malioc не может посчитать длинный путь, а циклы не удалось прогнать (ниже), в цене стоит «всего», поднятое по каждому блоку до короткого пути, и путь помечен как total.

Динамические циклы и n#

Цикл, число итераций которого известно только при выполнении: источники света Forward+ на пиксель, пробы, шаги луча. malioc не знает, сколько будет итераций, и самый длинный путь для такого шейдера не считает (N/A).

ParetoGPU переписывает каждый такой цикл так, чтобы он выполнился ровно n раз, замеряет шейдер при n = 0, 1, 2 и продолжает линейно:

цена(n) = цена(1) + (n − 1) × (цена(2) − цена(1)), цена(0) замеряется отдельно
  • Внешние динамические циклы получают n итераций, вложенные в них — одну (например, одно слово маски кластера на источник).
  • В отчёте кадра по умолчанию n = 2, таблица «Кадр при n итераций» показывает n = 0, 1, 2, 4, 8. В сравнении материалов n переключается.
  • Циклы с постоянной границей не трогаются: их malioc считает сам.

Цена вершины#

Mali (IDVS) делит вершинный шейдер на две части: Position (позиция, считается для всех вершин) и Varying (остальные выходы, только для видимых треугольников). Цена вершины = Position + Varying, то есть оценка сверху: часть вершин Varying не выполняет.

Выходы вершинного шейдера пишутся в память, поэтому у вершин частый упор — LS.

Регистры, spilling, fp16#

  • Рабочие регистры — сколько регистров нужно одному потоку. До 32 — ядро держит максимум потоков. Больше 32 — вдвое меньше потоков одновременно (occupancy 50%), и ядро хуже прячет задержки памяти и текстур, хотя в цене malioc этого не видно.
  • Spilling — регистров не хватило даже так, и переменные выгружаются в память (стек) и читаются обратно. Это нагрузка на LS и почти всегда заметное удорожание.
  • fp16 — доля вычислений в half (16 бит). На Mali half вдвое дешевле float в FMA и занимает вдвое меньше регистров. В отчёте помечается, если её меньше 25%.

Цена кадра#

draw = пиксели × цена пикселя + вершины × цена вершины; dispatch = потоки × цена потока

Цена кадра — сумма по всем событиям, в млн циклов на выбранном ядре. У каждого события своя доля кадра; события группируются по стадии, шейдеру, варианту, объекту и render target.

Отсюда: шейдер на 10% дешевле экономит 10% только своей доли кадра. Дешёвый шейдер на весь экран может стоить кадру больше дорогого на маленьком объекте.

Вариант шейдера — шейдер + проход + keywords: именно он компилируется и замеряется. Один шейдер с разными keywords — разные варианты с разной ценой.

Сравнение кадров#

События двух расчётов сопоставляются по варианту шейдера, а не по номеру. Разница B − A каждого варианта делится на три части:

  • Цена — шейдер стал дешевле или дороже на пиксель / вершину: эффект правки шейдера.
  • Объём — шейдер рисует больше или меньше пикселей / вершин: ракурс, сцена, LOD, перерисовка.
  • Состав — варианты, которые есть только в A или только в B: поменялись keywords, шейдер добавили или убрали.
цена = (pB − pA) × (wA + wB) / 2; объём = (wB − wA) × (pA + pB) / 2; цена + объём = B − A

Тот же снимок, посчитанный дважды (пересчёт после правки), даёт только цену: пиксели и вершины одинаковые.

Сравнение материалов#

  • Вариант материала = его шейдер, цветные проходы, keywords материала и глобальные keywords пайплайна для прохода (свет, тени, туман, Forward+), взятые из снимков кадра проекта.
  • Без снимков глобальные keywords не добавляются, а проходы берутся все, кроме служебных (тени, глубина, Meta).
  • Проходы A и B сопоставляются по имени, остальные по порядку.
  • Показывается цена пикселя и вершины без кадра: пиксели × цена считать не на чем. Чтобы узнать вклад в кадр, сравните кадры до и после замены материала.
  • «Дешевле на X%» считается от цены более дорогого из двух.

Разбор материала#

Вкладка «Материал»: выбираете один материал, ParetoGPU компилирует его варианты (keywords материала + глобальные keywords пайплайна, цветные проходы) и показывает цены, упор и конвейеры, а ниже — какие строки кода шейдера сколько стоят.

Как считается (абляция). Каждая строка x = выражение; в main() по очереди заменяется новым varying того же типа, и шейдер замеряется malioc заново. Компилятор выбрасывает выражение и всё, что считалось только для него, поэтому падение цены — это цена строки вместе с её хвостом. Динамические циклы прогоняются n раз, как в отчёте кадра.

ЧтоЗначение
Частьстрока вместе со всем, что без неё стало бы мёртвым кодом: значения, которые нужны только ей, и циклы и условия, которые после этого ничего не считают. Клик — её строки в коде и самые дорогие подчасти
Что внутричто делает часть, по всем её строкам: чтения буферов по индексу (свет и пробы Forward+), выборки текстур, хэш на sin, sin/cos/atan, pow/exp/log, корни и нормализации, деления, производные, целочисленные операции, строки матриц, сравнения и выбор; «в цикле (×n)» — часть в динамическом цикле

Доляэкономия в процентах от цены шейдера

↻строка в динамическом цикле: её цена — за n итераций
  • Не складывается. Цена шейдера — максимум по блокам, поэтому экономии частей не суммируются в цену: две части по 8 циклов вместе могут дать и 8, и 16. По одному блоку (A, LS…) складывается примерно.
  • Шум у отдельных строк. malioc считает такты с шагом, а расписание после удаления строки меняется: у строк длинной цепочки собственная цена скачет (0, 0.125, 0.5…), хотя сумма верна. Части устойчивее строк.
  • Вершины обычно упираются в LS — запись выходов, а её удалением строк не убрать: экономия цены там часто 0, и сортировка сама переключается на арифметику.
  • Код и цены — GLES-вариант. В Vulkan-варианте Unity (SPIR-V) не остаётся имён текстур и переменных, показать его строки нельзя. Цены GLES немного отличаются от Vulkan, но какие части тяжёлые — почти одинаково. Сами цены материала вверху — по выбранному API.
  • Новый varying сам стоит немного в V — поэтому у V бывают отрицательные значения.
  • Каждая строка — отдельный запуск malioc на каждом ядре разбора (по умолчанию только Mali-G78). Повторный разбор того же варианта берётся из кэша.

Перенос в вертекс#

Значение пиксельного шейдера, которое аффинно зависит от varying с коэффициентами из свойств материала или времени, можно точно посчитать в вершинном шейдере и передать через Custom Interpolator: интерполяция — взвешенное среднее с суммой весов 1, и линейное преобразование с ней перестановочно.

ПереноситсяНе переносится
Tiling / Offset: uv * _ST.xy + _ST.zwвсё, что прошло через текстуру (Rotate на угол из шума)
Rotate на угол из свойства: sin / cos считаются от свойства, uv только умножаетсянелинейные функции от varying: normalize, sin(uv), pow
Flipbook: номер кадра от времени, uv масштабируется и сдвигаетсяпроизведение двух varying, gl_FragCoord
смещения выборок в блюре: uv ± offset * kзначения из веток и циклов (зависят от пикселя)
  • Экономия — абляция той же строки: она заменяет значение новым varying, ровно как перенос. В ней уже учтена цена интерполяции нового varying; зато в вершинном шейдере добавятся те же вычисления на каждую вершину (вершин обычно в разы меньше, чем пикселей).
  • Одни сдвиги (uv + offset) не предлагаются: лишний varying стоит больше, чем одно сложение.
  • Компонент — сколько места займёт значение. Mali интерполирует varyings по 4 компоненты: у vec3 и vec2 свободные компоненты можно занять без нового слота.
  • Это только список: шейдер не переписывается.

Почему тяжёлые шейдеры#

«Отчёты» → снимок → «Почему тяжёлые» (или кнопка после проверки кадра): 10 самых дорогих вариантов шейдеров кадра на основном ядре разбираются по строкам, как в разборе материала. Вершинный шейдер разбирается, если он даёт хотя бы четверть цены варианта.

  • Что тяжёлое в сводке — самая дорогая часть ниже выхода шейдера: если одна часть — почти весь шейдер, показывается её самая дорогая подчасть.
  • Доли — от цены самого шейдера, а вклад шейдера в кадр — в колонке «% кадра».
  • Нужен GLES-вариант шейдера: если снимок считался с «Только Vulkan», разбор по строкам недоступен.

Как измерялись функции#

  • Единица «FMA» — стоимость одной скалярной highp FMA (a*b+c) на том же GPU. У разных GPU такты в разном масштабе, а в FMA видно, сколько «обычных операций» стоит функция: «sin = 8» — sin стоит как 8 умножений-сложений. Сырые такты есть в подробностях (клик по строке).
  • Уровни: дешёвая ≤ 1.5 FMA, средняя ≤ 10, тяжёлая > 10.
  • Почему на новых GPU функции «дорожают». Они не стали медленнее: например, sqrt на ядре G78 занимает 0.25 такта, на G715 — 0.125, на Mali G2 — 0.0625. Но в G715 и 5th Gen блоки FMA удвоили, а блок спецфункций (SFU) — нет, поэтому относительно обычной арифметики sqrt, деление, sin, exp подорожали вдвое. На таких GPU выгоднее экономить именно на этих функциях. На старых Bifrost, наоборот, сама FMA медленная, поэтому спецфункции там выглядят дешёвыми.
  • Цифры относятся только к Mali (Android на MediaTek, старых Exynos, Kirin, Google Tensor G1–G4). У Adreno (Snapdragon), Apple GPU и Xclipse (Exynos 2022+) они другие.
  • Каждая функция компилируется в цепочку из 8 и 24 зависимых вызовов x = f(x, a) + w во фрагментном шейдере (если не хватает регистров — 8 и 16 или 4 и 8). Стоимость — разница тактов на один вызов минус та же цепочка без функции. Операнды берутся из varying, чтобы компилятор не свернул вычисления.
  • Стоимость маргинальная, то есть сколько функция добавляет к реальному коду. Поэтому умножение в конце функции сливается со следующим сложением в FMA: pow(x, 2) и radians стоят ≈0, а log10 — как log2. Исключение — строки add, mul и mad: это сами базовые операции, они меряются цепочкой без + w (x = x * a), поэтому mul = 1. abs, saturate и f16tof32 часто бесплатны, потому что это модификаторы операндов.
  • Блок функции — где внутри GPU она считается: FMA, CVT или SFU (что в каком; на G615/G715 и 5th Gen сдвиги и побитовые операции в CVT, на G57–G710 — в SFU). Блоки работают параллельно: функция в CVT или SFU в шейдере, где в основном умножения и сложения, может оказаться частично бесплатной, а много SFU-функций подряд упрутся в SFU. У Bifrost блок один — «ALU». «—» — бесплатно: компилятор встраивает операцию в соседнюю инструкцию.
  • Аппроксимация ×N — есть более дешёвая формула с близкой точностью, N — во сколько раз она быстрее (медиана по GPU). Выигрыш — для функции отдельно: если шейдер и так упирается в FMA, он меньше.
  • Тест написан на GLSL. Unity (без #pragma use_dxc) переводит HLSL через FXC и HLSLcc, и часть функций там разворачивается иначе: например, atan2, asin и acos FXC раскладывает в полиномы сам, а sign в HLSL возвращает int. Для таких функций цена в Unity может отличаться.
  • Это статическая оценка компилятора, а не замер на устройстве: она хороша для сравнения функций между собой.

Единица FMA#

В таблице функций цена — не в тактах, а в FMA: во сколько раз функция дороже одной скалярной highp FMA (a*b+c) на том же GPU. «sin = 8» — sin стоит как 8 умножений-сложений. Так функции можно сравнивать между GPU с разной шириной блоков. В отчётах кадра и сравнениях цены — в тактах.

Как пользоваться#

Проверка кадра

  1. Откройте проект в Unity и выставьте в окне Game нужный кадр (обычно в Play Mode).
  2. Выберите проект во вкладке «Проверка кадра» и нажмите «Проверить кадр».
  3. Через несколько минут там появится цена кадра и самые дорогие шейдеры на Mali, а полный отчёт — во вкладке «Отчёты».

Пиксели: «Быстро» — Frame Debugger, сколько пикселей поменял каждый draw (хватает для поиска дорогих шейдеров); «Точно» — сколько раз реально выполнился пиксельный шейдер, с перерисовкой (нужен RenderDoc, загруженный в Unity: Game → Load RenderDoc).

Пересчёт. Поправили шейдер — откройте «Отчёты» и нажмите «Пересчитать» у снимка: тот же кадр посчитается с новыми ценами, и в «Сравнении» разница будет только от шейдеров.

Сравнение материалов. Во вкладке «Сравнение» → «Материалы» выберите проект и материалы A и B: начните вводить имя, путь или шейдер, или перетащите .mat из проводника в поле. «Сравнить» — Unity (редактор должен быть открыт) скомпилирует варианты шейдеров с keywords материалов, malioc их замерит. Будет цена пикселя и вершины на каждом Mali, в том числе при разном n. Прошлые сравнения — в списке справа.

Разбор материала. Вкладка «Материал»: выберите проект и материал (поиск или перетащите .mat) и нажмите «Разобрать». Нужен открытый редактор Unity. Будет всё о шейдере материала и самые тяжёлые части его кода.

Vulkan и GLES#

Unity компилирует шейдер для Vulkan (SPIR-V) и OpenGL ES (GLSL) разными путями, и драйвер Mali получает разный код. Цены одного шейдера в двух API могут заметно отличаться, а иногда меняется и то, какой из двух шейдеров дешевле. Смотрите тот API, на котором работает игра. По умолчанию — Vulkan.

Ограничения#

  • Это статическая оценка компилятора, а не замер на устройстве.
  • Не учитываются промахи кэша, пропускная способность памяти, задержки текстур, отброс пикселей по глубине (early-ZS), тайловая память и пропускная способность шины.
  • Цена по самому длинному пути — оценка сверху для ветвистых шейдеров.
  • Хороша для сравнения шейдеров между собой на одном ядре и для поиска самых дорогих в кадре.
