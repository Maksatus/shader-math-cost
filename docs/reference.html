Циклы на пиксель#

Цена шейдера — сколько циклов ядро Mali тратит на один его запуск: на один пиксель (фрагментный шейдер), один vertex (vertex) или один поток (compute). Её считает Mali Offline Compiler (malioc) для каждого ядра, без устройства.

цена = сумма циклов всех units ядра (A + LS + V + T) на самом длинном пути через шейдер

Ниже — что это за блоки, почему они складываются и что такое самый длинный путь.

Это не миллисекунды. Цена показывает, сколько работы шейдер даёт ядру. Сравнивать её стоит между шейдерами на одном ядре.

Блоки ядра Mali#

В шейдерном ядре Mali несколько units (pipes). По устройству они могут работать одновременно, но на деле почти не перекрываются (ниже).

Как A складывается из частей. На G57–G78 A — самая загруженная из FMA, CVT и SFU (они работают параллельно). На G310, G510, G610 и G710 части делят выдачу команд: A = max(FMA + CVT + SFU/4, SFU). На G615/G715 и 5th Gen — между этими крайностями. У Bifrost (G52) unit арифметики один, частей malioc не показывает. Цена шейдера в отчётах берёт A так, как его считает malioc; таблица функций — по тем же формулам для G57–G710, а для G615/G715 и 5th Gen — самую загруженную часть (чуть ниже A).

Сумма units и bottleneck#

malioc от Arm оценивает шейдер по самому загруженному unit, как будто остальные полностью прячутся за ним. Счётчики Mali на телефонах (G78, G710) показывают другое: ядро занято 64–94% от суммы циклов всех units и лишь в 2–3 раза больше самого загруженного. Блоки ждут друг друга (арифметике нужен результат текстуры), варпов мало, чтобы заполнить паузы. Поэтому цена — сумма units: она ближе к железу и меньше путает, что из двух шейдеров дороже (сверка).

Bottleneck — самый загруженный unit. В отчётах он показан как «LS память», «SFU спецфункции» и т.п. Он подсказывает, где у шейдера больше всего работы, но цену дают все блоки.

Пример: LS 36, арифметика 21, T 4.3 → цена 61.3, bottleneck LS. Убрать половину математики: цена станет 50.8.

Если упоров два (например FMA+CVT), они загружены одинаково.

Пути: длинный, короткий, всего#

  • Самый длинный путь — самый дорогой путь через шейдер: каждый if идёт по более дорогой ветке. Цена считается по нему, то есть это оценка сверху для одного запуска.
  • Самый короткий путь — все ветки идут по дешёвой стороне. Вместе с длинным даёт разброс.
  • Всего — каждая инструкция посчитана один раз: обе ветки if, тело цикла один раз. Это объём кода, а не время: может быть и больше, и меньше длинного пути.

Если malioc не может посчитать длинный путь, а циклы не удалось прогнать (ниже), в цене стоит «всего», поднятое по каждому unit до короткого пути, и путь помечен как total.

Динамические циклы и n#

Цикл, число итераций которого известно только при выполнении: источники света Forward+ на пиксель, пробы, шаги луча. malioc не знает, сколько будет итераций, и самый длинный путь для такого шейдера не считает (N/A).

ParetoGPU переписывает каждый такой цикл так, чтобы он выполнился заданное число раз, и замеряет каждый внешний цикл отдельно: он на M, 2M и 4M итерациях (M = 32), все остальные на 1. При нескольких итерациях malioc разворачивает цикл и держит чтения uniform в регистрах, а настоящий динамический цикл читает их на каждой итерации, поэтому прямая строится по большим n. Цена шейдера — база плюс вклад каждого цикла при его числе итераций nk:

цена = база + Σ fk(nk), fk(n) = одинk − база + (n − 1) × наклонk
  • База — все внешние циклы по одной итерации. Наклон и «один» (цена цикла на одной итерации) — по каждому unit ядра из прямой через M и 2M, если шаг до 4M с ней сходится (в пределах 3%), иначе через 2M и 4M. Наклон не меньше нуля.
  • Цикл с проверкой выхода в заголовке (for (i < n)) при n < 1 идёт к замеру на 0 итераций: fk(n) = (1 − n) × fk(0) + n × fk(1). Если на 0 стоят все такие циклы, цена ведётся к отдельному замеру «все на 0»: компилятор выбрасывает то, что они считали. Цикл while (true) с выходом в теле (обход маски кластера, пробы) и на 0 итераций проходит свою проверку, поэтому его прямая продолжается ниже 1.
  • Если у цикла свой постоянный предел (луч SSR, 24 шага) или malioc на 4M не считает путь, прямая на M…4M не растёт ровно: M уменьшается вдвое, вплоть до 1, пока шаги не сойдутся.
  • Вложенные циклы идут по одной итерации на итерацию своего внешнего (например, одно слово маски кластера на 32 источника) и из наклона вычитаются.
  • Одно n для всех циклов — та же формула с равными nk. В подробностях events отчёта frame видно, во сколько обходится каждый цикл шейдера.
  • Если граница цикла — параметр шейдера (например, for (i < min(_Count.w, 128))), число повторов берётся из значения этого параметра у вызова в frame: граница прослеживается по SPIR-V варианта до смещения в uniform-блоке, значение читается из байтов этого unit в захвате RenderDoc. Так же на ПК и на телефоне. Дробная граница округляется вверх (i < 2.5 — 3 повтора).
  • Цикл фрагментного шейдера, граница которого не параметр (обход маски кластера: источники и пробы на пиксель, значение из буфера), считается при snapshot frame по захвату RenderDoc подменой шейдера: draw переигрывается с тем же шейдером, в котором в конце каждого внешнего цикла стоит счётчик, а выход — число итераций вместо цвета. Пиксели вызова — те, у которых он изменил цвет или глубину (у draw без записи глубины цель перед вызовом очищается); n — среднее по пикселям всех вызовов events. Так же на ПК и на телефоне (захват переигрывается на самом телефоне). Расхождение потоков в варпе (варп идёт столько, сколько самый долгий пиксель) не учитывается.
  • Если повторы такого цикла сосчитать не удалось, расчёт останавливается с ошибкой: цена на угаданном n не пишется.
  • У vertex и compute-шейдера цикл без параметра в границе идёт при n = 2 (в подробностях events — «по умолчанию»). В сравнении материалов n по умолчанию 2 и переключается: 0, 1, 2, 4, 8.
  • Циклы с постоянной границей не трогаются: их malioc считает сам.

Цена vertex#

Mali (IDVS) делит vertex шейдер на две части: Position (позиция, считается для всех vertices) и Varying (остальные выходы, только для видимых треугольников). Цена vertex = Position + Varying, то есть оценка сверху: часть vertices Varying не выполняет.

Выходы vertex шейдера пишутся в память, поэтому у vertices частый bottleneck — LS.

Регистры, spilling, fp16#

  • Рабочие регистры — сколько регистров нужно одному потоку. До 32 — ядро держит максимум потоков. Больше 32 — вдвое меньше потоков одновременно (occupancy 50%), и ядро хуже прячет задержки памяти и текстур, хотя в цене malioc этого не видно.
  • Spilling — регистров не хватило даже так, и переменные выгружаются в память (стек) и читаются обратно. Это нагрузка на LS и почти всегда заметное удорожание.
  • fp16 — доля вычислений в half (16 бит). На Mali half2 и half4 в FMA идут вдвое быстрее float (скалярный half — как float; на весь шейдер выигрыш обычно меньше: другие pipes от half не ускоряются вдвое) и занимает вдвое меньше регистров. В отчёте помечается, если её меньше 25%.

Цена frame#

draw = пиксели × цена пикселя + vertices × цена vertex; dispatch = потоки × цена потока

Цена frame — сумма по всем events, в млн циклов на выбранном ядре. У каждого events своя доля frame; events группируются по стадии, шейдеру, варианту, объекту и render target.

Отсюда: шейдер на 10% дешевле экономит 10% только своей доли frame. Дешёвый шейдер на весь экран может стоить frame больше дорогого на маленьком объекте.

Вариант шейдера — шейдер + pass + keywords: именно он компилируется и замеряется. Один шейдер с разными keywords — разные варианты с разной ценой.

Сравнение frames#

Snapshot с ПК против snapshot с телефона — отдельный вид «Модель ПК и замер телефона»: по каждому шейдеру и стадии цена модели ПК на ядре телефона (snapshot ПК должен быть посчитан с этим ядром) рядом с замером подменой: цвет пиксельного шейдера против фрагментных циклов модели, «draw целиком» против полной цены draw. Это проверка модели; разница в 1.5 раза и больше выделена. Сцены должны совпадать: на VATyakov в редакторе плоскость рисуется до толпы и закрашивается целиком, на телефоне — после, поэтому у Lit модель ×6.7.

Events двух расчётов сопоставляются по варианту шейдера, а не по номеру. Разница B − A каждого варианта делится на четыре части:

  • Цена — шейдер стал дешевле или дороже на пиксель / vertex при одном и том же числе повторов циклов: эффект правки шейдера.
  • Повторы циклов — динамические циклы шейдера (свет, пробы, шаги луча) повторяются больше или меньше раз: это сцена, а не код. Например, 3 и 6 источников света на тот же пол.
  • Объём — шейдер рисует больше или меньше пикселей / vertices: ракурс, сцена, LOD, overdraw.
  • Состав — варианты, которые есть только в A или только в B: поменялись keywords, шейдер добавили или убрали.
цена = (rB − rA) × (wA + wB) / 2; повторы циклов = (pB − pA) × (wA + wB) / 2 − цена; объём = (wB − wA) × (pA + pB) / 2; цена + повторы + объём = B − A

p — цена варианта на пиксель / vertex, r — она же при одном повторе каждого цикла (от сцены не зависит). Если у варианта в A и B одинаковое число повторов каждого цикла, вся разница цены — «цена» (правка тела цикла тоже туда). Тот же snapshot, посчитанный дважды (пересчёт после правки), даёт цену и, если число повторов бралось по-разному, повторы циклов: пиксели и vertices одинаковые.

Сравнение материалов#

  • Вариант материала = его шейдер, цветные passes, keywords материала и глобальные keywords пайплайна для pass (свет, тени, туман, Forward+), взятые из snapshots frame проекта.
  • Без snapshots глобальные keywords не добавляются, а passes берутся все, кроме служебных (тени, глубина, Meta).
  • Passes A и B сопоставляются по имени, остальные по порядку.
  • Показывается цена пикселя и vertex без frame: пиксели × цена считать не на чем. Чтобы узнать вклад в frame, сравните frames до и после замены материала.
  • «Дешевле на X%» считается от цены более дорогого из двух.

Как измерялись функции#

  • Единица «FMA» — стоимость одной скалярной highp FMA (a*b+c) на том же GPU. У разных GPU циклы в разном масштабе, а в FMA видно, сколько «обычных операций» стоит функция: «sin = 8» — sin стоит как 8 умножений-сложений. Сырые циклы есть в подробностях (клик по строке).
  • Уровни: дешёвая ≤ 1.5 FMA, средняя ≤ 10, тяжёлая > 10.
  • Почему на новых GPU функции «дорожают». Они не стали медленнее: например, sqrt на G78 занимает 0.25 цикла (8 FMA), на G715 и G720 — 0.125 цикла, но уже 16 FMA: unit FMA там ускорили вчетверо, а unit спецфункций (SFU) — вдвое, поэтому относительно обычной арифметики sqrt, деление, sin, exp подорожали вдвое. На таких GPU выгоднее экономить именно на этих функциях. На Mali G1 и G2 SFU снова расширили, и в FMA они стоят как на G78. На старых Bifrost, наоборот, сама FMA медленная, поэтому спецфункции там выглядят дешёвыми.
  • Цифры относятся только к Mali (Android на MediaTek, старых Exynos, Kirin, Google Tensor G1–G4). У Adreno (Snapdragon), Apple GPU и Xclipse (Exynos 2022+) они другие.
  • Каждая функция компилируется в цепочку из 8 и 24 зависимых вызовов x = f(x, a) + w во фрагментном шейдере (если не хватает регистров — 8 и 16 или 4 и 8). Стоимость — разница циклов на один вызов минус та же цепочка без функции. Операнды берутся из varying, чтобы компилятор не свернул вычисления.
  • Стоимость маргинальная, то есть сколько функция добавляет к реальному коду. Поэтому умножение в конце функции сливается со следующим сложением в FMA: pow(x, 2) и radians стоят ≈0, а log10 — как log2. Исключение — строки add, mul и mad: это сами базовые операции, они меряются цепочкой без + w (x = x * a), поэтому mul = 1. abs, saturate и f16tof32 часто бесплатны, потому что это модификаторы операндов.
  • Unit функции — где внутри GPU она считается: FMA, CVT или SFU (что в каком; на G615/G715 и 5th Gen сдвиги и побитовые операции в CVT, на G57–G710 — в SFU). Блоки работают параллельно: функция в CVT или SFU в шейдере, где в основном умножения и сложения, может оказаться частично бесплатной, а много SFU-функций подряд упрутся в SFU. У Bifrost unit один — «ALU»; на G310–G710 «ALU» — когда цену задаёт общая выдача команд FMA + CVT + SFU/4, а не один unit. «—» — бесплатно: компилятор встраивает операцию в соседнюю инструкцию.
  • Аппроксимация ×N — есть более дешёвая формула с близкой точностью, N — во сколько раз она быстрее (медиана по GPU). Выигрыш — для функции отдельно: если шейдер и так упирается в FMA, он меньше.
  • Тест написан на GLSL. Unity (без #pragma use_dxc) переводит HLSL через FXC и HLSLcc, и часть функций там разворачивается иначе: например, atan2, asin и acos FXC раскладывает в полиномы сам, а sign в HLSL возвращает int. Для таких функций цена в Unity может отличаться.
  • Это статическая оценка компилятора, а не замер на устройстве: она хороша для сравнения функций между собой.

Единица FMA#

В таблице функций цена — не в циклах, а в FMA: во сколько раз функция дороже одной скалярной highp FMA (a*b+c) на том же GPU. «sin = 8» — sin стоит как 8 умножений-сложений. Так функции можно сравнивать между GPU с разной шириной units. В отчётах frame и сравнениях цены — в циклах.

Как пользоваться#

Проверка frame

  1. Откройте проект в Unity на Vulkan (-force-vulkan) с RenderDoc, загруженным при запуске (-load-renderdoc или Game → Load RenderDoc до первого frame), включите Play Mode и выставьте в окне Game нужный frame. Без Play Mode frame не снимается: в редакторе без запущенной игры frame не тот, что на устройстве.
  2. Выберите проект во вкладке «Проверка frame» и нажмите «Проверить frame».
  3. Через несколько минут там появится цена frame и самые дорогие шейдеры на Mali, а полный отчёт — во вкладке «Отчёты».

Frame с телефона. Нужны adb и RenderDoc for Arm GPUs (из Arm Performance Studio). Выберите телефон (USB) вместо проекта и нажмите «Проверить frame»: игра запустится на телефоне (development build, Vulkan). Откройте нужную сцену и нажмите ту же кнопку — теперь она «Снять frame»; после этого телефон не трогать. Snapshot такой же, как из редактора, и считается так же; OnGUI и надпись Development Build в него не входят.

Настройки frame — строка под заголовком отчёта: размер и масштаб frame, MSAA и формат основной цели, карты теней и passes. Они прочитаны из самого frame, поэтому одинаковы для любого пайплайна и для ПК и телефона: если у двух snapshots они разные, «Сравнение» предупредит — frames сняты с разными настройками рендера.

Пересчёт. Поправили шейдер — откройте «Отчёты» и нажмите «Пересчитать» у snapshot: тот же frame посчитается с новыми ценами, и в «Сравнении» разница будет только от шейдеров. Если сцена включает свой пайплайн-ассет только в Play Mode, пересчитывайте в Play Mode: иначе у редактора другой набор вариантов.

Сравнение материалов. Во вкладке «Сравнение» → «Материалы» выберите проект и материалы A и B: начните вводить имя, путь или шейдер, или перетащите .mat из проводника в поле. «Сравнить» — Unity (редактор должен быть открыт) скомпилирует варианты шейдеров с keywords материалов, malioc их замерит. Будет цена пикселя и vertex на каждом Mali, в том числе при разном n. Прошлые сравнения — в списке справа.

Как снимается frame#

ПК и телефон идут одним pipe Vulkan / SPIR-V, поэтому их snapshots сравнимы.

  • Редактор работает на Vulkan. RenderDoc снимает frame (геометрия, вызовы, счётчики, байты uniform-блоков каждого вызова), Frame Debugger даёт вариант шейдера каждого events: шейдер, pass, keywords.
  • Код вариантов — из «Compile and show code» Unity (тот же компилятор, что у сборки): текст SPIR-V собирается обратно утилитой spirv-as из RenderDoc и совпадает с кодом сборки на телефоне байт в байт. Есть только те варианты, которые попали бы в сборку, поэтому пайплайн-ассет редактора должен быть тот же, что у frame. Snapshot хранит ассет frame (путь и хэш; у телефона — ассет сборки из настроек качества Android). Если при пересчёте в редакторе активен другой ассет и вариантов frame нет, пересчёт останавливается с подсказкой: включите Play Mode или тот же ассет. Если ассет тот же, у draw без цены написано, каких keywords frame нет ни в одном варианте сборки.
  • Телефон — RenderDoc for Arm GPUs: захват development build по adb и replay на самом телефоне, в одном процессе. Draw опознаются по коду шейдера, их pass (LightMode, а по нему стадия) — по таблице passes проекта из редактора.
  • Состояние вызовов (SPIR-V шейдеров, байты uniform-блоков, цели, смешивание, глубина, индексы) читается из структуры захвата без переигрывания: создание объектов, начальное содержимое памяти и наборов дескрипторов, записи в память и обновления дескрипторов до отправки frame. На ПК draw с фрагментным шейдером переигрываются по одному ради треугольников после vertex шейдера и повторов циклов. На телефоне этого обхода нет: каждый переход replay там переигрывает frame с начала (~0.2 с, минуты на frame), а что тяжелее, показывает замер подменой шейдеров.
  • Пиксели — квады 2×2 по геометрии захвата, повторы циклов — подменённым шейдером-счётчиком (ПК). На snapshot с телефона модель грубее: пиксели — Samples Passed, повторы циклов без параметра — по умолчанию (2).
  • Цены — malioc по SPIR-V вариантов для каждого ядра Mali.

Итог модели сверяется со счётчиками Mali: на живой игре — Streamline (streamline_me.py --headless, счётчики G78 и слой GPU timeline, Streamline-cli -report), на захваченном frame — RenderDoc for Arm (счётчики Mali по passes, один запрос). VATyakov K31_Heavy, Galaxy S21 (G78 MP14), 15.10.2026:

Эта сумма сходилась за счёт ошибок, которые компенсировали друг друга. Сверка по 40 passes (счётчики RenderDoc for Arm: циклы исполнения, выдача в pipes A / LS / T / V, потоки и варпы) показала три ошибки модели, и они исправлены:

  • Load/store. malioc считает каждое обращение как один поток за цикл, а массив uniform-блока с вычисляемым индексом — ещё втрое дороже, как разрозненную выборку. На G78 счётчик LS в 4–12 раз ниже: обращения варпа сливаются (64 байта за цикл, четыре потока по 16 байт), а индексы массивов (счётчик цикла, номер источника света) у потоков варпа совпадают. Теперь LS на Valhall и новее делится на 4, а массивы uniform-блоков с вычисляемым индексом malioc меряет как storage buffer. После правки LS модели совпадает со счётчиком: Bokeh DOF 6.8 / 6.8 млн, тени 15.5 / 18.0 и 13.4 / 16.3, непрозрачный pass 237 / 195.
  • Vertices без фрагментного шейдера. В passes теней Mali не запускает Varying-вариант (0 потоков), поэтому для draw без фрагментного шейдера считается только Position. Pipe A теней совпал со счётчиком: 40.0 / 39.8 и 35.6 / 35.7 млн.
  • Потоки драйвера в тайле. Драйвер Mali запускает свои фрагментные потоки: по одному на сэмпл MSAA-цели (очищенной или загруженной), по одному на пиксель resolve в тайле и по одному на сэмпл загружаемой глубины. Однократная (не MSAA) цвет-цель грузится без потоков. Каждый поток стоит 2.1 цикла, по замеру на pass очистки с resolve без draw. В отчёте это строки «тайл Mali». Pass без draw: 27.2 / 27.6 млн, прозрачный pass: 53.0 / 52.9 млн.

После правок модель даёт 581 млн циклов против 1044 млн «исполнение активно» на железе. Bokeh DOF — ×0.65 (было ×3.6), непрозрачный pass — ×0.65 (было ×1.7), прозрачный — ×1.00 (было ×0.27). Оставшиеся расхождения не исправлены, им нужна своя модель:

  • Passes с одной геометрией (тени, DepthNormals): работа шейдера совпадает, но ядра в 3.6–5 раз дольше ждут tiler. Он упирается в задержку позиционного шейдинга: позиция считается пачками по 4 vertices, тени тратят около 3.1 цикла GPU на треугольник. Тени — ×0.27, DepthNormals — ×0.22. Поэтому passes теней и глубины (stage shadow / prepass) не входят в итог frame: отчёт показывает их отдельной таблицей «Не считается на ПК» (draw, vertices, треугольники), их настоящая нагрузка — в snapshot с телефона.
  • Фрагментные passes: на G78 pipes почти не перекрываются. Время исполнения на железе — 0.64–0.94 от суммы A + LS + T + V и 1.1–2.3 от максимума. С 16.10.2026 цена — сумма pipes: frame VATyakov на S21 1100 / 1036 млн (было 580), на Pixel 7 (G710) 66 / 80 (было 41); из пар passes «что дороже» верно 33 из 36 (было 28).
  • Мелкие passes (CopyColor, малые passes DOF, Bloom) по 1–4 млн циклов — накладные расходы pass, в сумме около 2% frame.

Snapshot с телефона — замер на GPU телефона (он же основное ядро отчёта). Отчёт тот же, что у snapshot с ПК, и итог собран по тем же правилам: сумма units, passes теней и глубины отдельно (их замер — в своей таблице), строки «тайл Mali» — по модели. Так итоги ПК и телефона сравнимы.

  • Цена шейдера. Frame проигрывается на телефоне по очереди с каждым шейдером-заглушкой. Пиксельный шейдер пишет ноль в цвет (тот же SPIR-V, discard и глубина остаются). Vertex выносит позицию за экран, и уходит вся работа его draw. Разница счётчиков — цена шейдера: сумма циклов units (арифметика, LS, текстуры, varying), как в модели. Каждый вариант снимается 3 раза, берётся медиана. Unit с разницей ниже нуля — шум, он не считается; если шейдер весь ниже шума или не подменён, у его draw остаётся цена модели, строка помечена «!», а отчёт пишет, сколько draw и какая доля итога взяты из модели.
  • Пиксели — Samples Passed на телефоне: сколько пикселей закрасил шейдер за frame, с overdraw, без пустых потоков квадов (на ПК — квады). Ими замер шейдера делится между его draw. Vertices — уникальные индексы draw × instances.
  • Цикл / пикс — цена пиксельного шейдера / его пиксели. У events цена шейдера делится по его пикселям, поэтому замер точен по шейдеру, а по events это доля замера.
  • Vertex часть — цена draw с подменённым vertex шейдером минус цена цвета тех же draw, по vertices.
  • Галочка --no-shader-cost выключает замер шейдеров, тогда таблицы нет.

Когда RenderDoc for Arm не снимает счётчики Mali (frame клиента: на Galaxy S21 драйвер падает в vkEndCommandBuffer вторичного буфера команд pass Draw Opaque + Draw Skybox с двумя подпроходами, на Pixel 7 зависает), цена шейдеров меряется через Streamline: frame проигрывается на телефоне целиком, по одному разу с паузами (сначала как снят, потом с каждым шейдером-заглушкой по три раза), а gatord, запущенный для процесса RenderDoc, пишет счётчики Mali. Вспышки работы GPU сопоставляются с реплеями по времени. Passes при этом не разделены (одна строка «весь frame»), циклы ядра шумят на несколько миллионов из-за служебной подгрузки ресурсов в каждом реплее, поэтому цена — сумма units, как и при замере через RenderDoc.

Модель против замера по passes (когда RenderDoc for Arm снял счётчики): циклы ядра сравниваются только по passes, которые модель считает; passes теней и глубины идут отдельной цифрой. Если в сборке на телефоне код draw не совпал ни с одним вариантом проекта (сборка старее проекта или с другим качеством), отчёт предупреждает.

Vulkan и GLES#

Unity компилирует шейдер для Vulkan (SPIR-V) и OpenGL ES (GLSL) разными путями, и драйвер Mali получает разный код. Цены одного шейдера в двух API могут заметно отличаться, а иногда меняется и то, какой из двух шейдеров дешевле.

Frames и материалы считаются только в Vulkan: код вариантов берётся из «Compile and show code» для Vulkan, как в сборке. Цены функций на сайте даны для обоих API.

Ограничения#

  • Это статическая оценка компилятора, а не замер на устройстве.
  • Не учитываются промахи кэша, пропускная способность памяти, задержки текстур и пропускная способность шины. Тест глубины (early-ZS) и потоки тайла считаются по квадам и строкам «тайл Mali»; Forward Pixel Kill — нет, overdraw непрозрачных draw считается целиком (худший случай).
  • Цена по самому длинному пути — оценка сверху для ветвистых шейдеров.
  • Хороша для сравнения шейдеров между собой на одном ядре и для поиска самых дорогих в frame.
